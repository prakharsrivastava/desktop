=== What is Agentic RAG ? - Advanced Reasoning: Agentic RAG ===


--- The Hard Parts: Challenges and Limitations of AI Agents ---

In this video, we are going to learn challenges and limitations of AI agents.
It is clear that AI agents has transformative potential from agriculture to healthcare to IT operations.
However, as architects and engineers, we know there is no such a thing as a magic solution.
With great power comes significant complexity and risk.
Our job is not just build what is possible, but to build what is robust, secure and reliable.
So now let's go to the our first and most fundamental challenge, which is the Non-determinism.
Traditional software is deterministic.
If you give a function the same input, you will get the exact same output every single time.
Like two plus two always equals four.
AI agents, because their brain is an LLM, are nondeterministic or stochastic.
This means that given the exact same goal, for example, summarize this email, an agent might produce
a slightly different summary today than it did yesterday.
It might choose a different plan or a different wording, but this isn't a bug to be fixed.
It is a core property of the technology.
This property, however, creates a massive challenge for us in testing and validation.
How do you write a unit test for correctness when the output is intentionally variable?
This is the ghost in the machine.
And this brings us to the next challenge, which is the security and guardrails.
In our use case, we celebrate giving agents tools, but we must remember that what these tools are.
They are APIs, database connections, and code interpreters.
We are giving an autonomous non-deterministic system.
The keys are Kingdom.
What happens when a sales agent, in a proceed of its call to close the sale?
Creativity decide to offer 90% discount.
What stops a well intentioned but Misconfigured agent.
Give a work call of the clean up the database from calling the delete all user command.
This is the fake agent problem.
Our critical architectural challenge is to design robust guardrails that enforce strict permissions
limiting and agents blast radius without stifling its autonomy.
So next challenge are the twin business realities.
These are the cost and latency.
First of all, let's start with the cost.
Agent groups are not cheap.
Every reasoning or planning step is at minimum one full LLM call.
A seemingly simple five step task could involve 10 or 15 separate large LLM calls.
So this can be thousands of times more expensive than running a traditional script.
A runway agent stuck in a loop could become a significant financial liability.
And the second problem is latency problem.
LLM calls are slow.
We measure them in seconds, not milliseconds.
A five step agent plan can easily take 30s or more to execute.

--- How Agentic AI Works: System-Level Architectures (Orchestration or Choreography) ---

In this video, we are going to learn how a genetic AI works in a system level architectures.
How do we actually design a system where multiple autonomous agents can work together effectively?
We will answer this by exploring the two primary architectural patterns that enable agent collaboration.
So now let's remember our core problem.
We have multiple autonomous agents, and each one is capable of perceiving, reasoning and acting independently.
And it has own goals and own tools.
So the challenge is how do we prevent this from becoming caused?
And how do we ensure these independent actors work together?
So we need a defined mechanism for decomposing the main task, assigning the subtasks, communicating
to progress, and synchronizing the actions.
So there are two primary architectural patterns we use to solve this coordination problem.
The first one is orchestration, which is a centralized, top down approach similar to having a manager
or a conductor.
The second is choreography, which is a decentralized bottom up approach, more like dancers reacting
to music or agents reacting to events on a shared message bus.
These patterns represent fundamentally different ways to structure the interactions within our AI system.
Let's analyze each one.
The first one is orchestration.
This is often more intuitive.
Pattern.
The core principle is centralization.
One agent is designated as the orchestrator or manager.
This agent receives the high level complex goal from the user.
It is job is not to execute the task itself, but to manage the workflow.
It uses its planning module to decompose the goal into a sequence of subtasks.
It then delegate each subtask to the appropriate specialist agent, for example, telling the inventory
agent to check stock, then telling the billing agent to process payment.
The orchestrator waits for each specialist to report back, synthesizes the results, and then decide
the next step in the plan.
It is a classic top down command and control structure.
A project manager is assigning tasks to team members.
Now let's see an example of the orchestrated customer service agent.
A customer service system is a perfect example of the orchestration.
The user asks a complex two part question.
User goal is what is the status of my recent order and can I add express shipping?
So the customer service agent acting as orchestrator received this and it starts with the planning and
it plans the two steps needed.
The first step is it delegate.
Step one by making a structured A to a call to the order agent, it waits for the response.
Then it delegates the step two by calling the shipping agent, it waits again.
And finally it synthesizes the results from both specialists and formulates the final answer for the
user.
You can notice that how the service agent explicitly controls the sequence and flow.
So now we can go to the next button, which is the choreography.
This is a decentralized, event driven pattern.
There is no central manager.
All agents are peers.
How do they coordinate?
They interact indirectly.
One agent performs an action, and this action either publish an event to a shared message bus like
Kafka or RabbitMQ, or directly changes a record in a shared database.
Other agents in the system are independently listening for specific events or state changes that are
relevant to them.
When they hear something interesting, they autonomously react by performing their own action, which
in turn might trigger yet another agent.
It is a chain reaction, like dancers responding to the music and each other's movements.
Now let's see an example about the choreography.
A supply chain is a classical example of choreography.
Goal is to fulfill any customer order.
There is no single manager agent coordinating the whole process.
Instead, the order agent simply perceives any order and acts by confirming it.
Publishing an order confirmed event.
The inventory event, which is independently listening for that event, reacts by decrementing stock
and publishing its own event.
After that, the shipping event listening for that event reacts by scheduling by delivery.
Each agent only knows about its own small part of the process and reacts to the event it cares about.
The overall fulfillment happens emergently from these independent interactions.
So now let's understand how to choose the right pattern.
So which pattern should you choose?
As always in architecture it depends on the trade offs.
Orchestration is generally simpler to design and understand.
The entire workflow logic is in one place, making it easier to debug.
However, it creates a single point of failure and can become a bottleneck.
It is also less flexible.
Adding a new step requires modifying the central orchestrator.
Choreography is far more flexible, scalable, and resilient.
There is no single point of failure, and you can easily add new agents listeners without changing the
existing ones.
However, it is much harder to monitor and debug the overall system.
Behavior is emergent, making it difficult to trace a single request.
There is also a high risk of the unintended consequences or infinite loops.

--- The Hard Parts: Challenges of Agentic AI Systems ---

In this video, we are going to learn the challenges of the AI systems.
In the previous lectures, we learned how to coordinate complex tasks in areas like e-commerce, disaster
response, and supply chain management.
However, this leap from a single component to a distributed system introduces an entirely new class
of architectural challenges.
As architects, we must approach these multi-agent systems with a clear understanding of these hard
parts.
Let's identify and analyze these challenges for our AI systems.
And our first challenge is system wide observability.
Debugging a single agent's internal monologue is already difficult.
But what happens when that thought is not happening in one brain, but is distributed across a team
of 510 collaborating agents?
It must be extremely difficult if the final result is wrong.
Tracing the root cause becomes exponentially harder.
Did the orchestrator agent make a bad plan, or did the inventory agent fail to execute its tool correctly?
Or did the agent simply misinterpret the message it received from the orchestrator, and the chain of
thought is now fragmented for the distributed agents.
So that means we must design robust distributed tracing and centralized logging systems specifically
for the agent interactions, just as we do for microservice architectures, but with the added complexity
of non-deterministic reasoning at each step.
After that, our second challenge is unique to complex system, which is emergent behavior.
Emergence occurs when the interactions of many simple agents lead to complex unplanned behaviors at
the system level.
This is both the power and the danger of the gigantic AI.
What happens when ten trading agents, each following the simple rules, interacting in a way that accidentally
crashes the market?
What if two agents in our supply chain get stuck in an infinite loop, constantly ordering and canceling
the same item?
So the system's behavior may become something that no single agent planned or intended or architectural
challenge is immense.
How do we design systems that allow for beneficial emergence while preventing the harmful emergent behaviors.
This often involves extensive simulation, careful agent design, and system wide guardrails.
So our next challenge is inter-agency communication.
Whether we use orchestration or choreography, pattern or system depends on agents successfully sending
and receiving messages.
This relies on stable communications like MCP or defined API contracts between agents.
These communication failures create the risk like protocol mismatch, API chains, and network failures.
So our architecture challenge is to design for resilient communication.
And this involves standard distributed system techniques, careful API reasoning, robust error handling,
retry mechanism and the patterns like circuit breakers to prevent cascading failures when one agent
becomes unresponsive.
Our final major challenge is goal conflict and resource allocation.
This is the classic concurrency problem now applied to autonomous agents.
What happens when two different agents operating independently need the same limited resource?
Imagine two separate travel agents, both trying to book the very last seat on a flight to New York
at the exact same millisecond.
Who gets it?
Or consider agents with conflicting goals a cost saving agent might decide to.
Optimal action is to shut down an underutilized server, while an uptime agent simultaneously decide
it needs that server as a backup.
This is a classic concurrency problem from distributed systems architecture.
Challenge is to implement mechanisms to resolve these conflicts.
This might involve establishing clear prioritization rules, implementing locking mechanisms for critical
resources, or even building negotiation protocols where agents can bid for a resource or compromise.
As a summary, we can say that the challenge of the gigantic AI are fundamentally systemic.
We must design for system wide observability.
To debug the distributed reasoning, we must manage emergent behavior to prevent harmful outcomes.
We must ensure resilient communication to avoid system brittleness, and we must implement mechanism
to resolve goal conflict and resource contention.

--- The "Swarm" Pattern (Parallelization) ---

In this video we are going to learn the swarm pattern.
In our last lecture we learned Groupchat pattern which is digital meeting room designed for creative
debate.
It is powerful for improving quality, but it is fundamentally sequential or agent speak at a time.
It is slow, deliberate and expensive.
But what if our problem isn't creatively complex, but just massive in scale?
What if we are not trying to design any marketing plan?
What if our task is summarize all 10,000 articles published yesterday?
We don't need a debate for this.
We don't need a handoff.
We need an army of agents all working at the same time.
This is the swarm pattern.
So now let's understand the swarm pattern in detail.
The swarm pattern is best understood as a beehive or an army.
It is an architecture where a central queen agent acts as the foreman.
It takes a massive list based, task like process.
10,000 of these files and decompose it into 10,000 small, identical subtasks.
It then spawns or invokes thousands of worker agents to execute all these subtasks in parallel.
The entire goal is to achieve a massive speedup on what we call in computer science embarrassingly parallel
problems tasks that can be broken up and require no communication between the workers.
The core concept.
This is the MapReduce design pattern applied to AI patterns.
So now let's understand the MapReduce architecture.
This pattern has two distinct phases, both managed by our Queen agent.
The first is the map phase.
This is decomposition and distribution.
The queen agent takes the large list like 1000 reports and maps it.
It iterates the list and spawns one worker agent for each item.
The worker agent logic is simple.
Summarize the one report you are given.
The second is the reduce phase.
This is aggregation and synthesizers.
The Queen agent waits for all a thousand workers to finish and return their individual summaries.
It then collects all these results.
Finally, it reduces them by performing one last action, such as writing a meta summary of all the
individual summaries into a single final output for the user.
So now let's trace this pattern in action.
So basically our task is summarize a thousand articles in this folder.
First of all the queen agent executes the map phase.
It doesn't read the articles.
It simply decompose the list into 1000 individual subtasks.
And second the worker agent execute in parallel.
Our orchestrator spawns 1000 instances of our summary agent logic.
And this might be massive async call in Python.
Or it could trigger 1000 separate serverless cloud functions, and each worker receives one document
and summarize it and return the result.
And the third step.
The queen agent begins the reduce phase.
It waits for all thousand parallel processes to complete it, and gather all 1000 individual summaries
into one massive list.
Finally, the queen agent synthesizes the result.
It makes one final call, feeding it all 1000 summaries with a prompt like write one page executive
summary of these summaries.
And this final aggregated answer is what's returned to the user?
And as architects, this pattern is a classic double edged sword.
The benefit is obvious and singular.
Massive speed and scale.
It can be literally thousands of times faster than trying to process the list in a single sequential
loop.
And the limitations, however, are severe.
First, it only works for embarrassingly parallel tasks.
The workers cannot talk to each other if they need to.
This pattern fails, and trade offs are also important for this swarm pattern.
This pattern is profoundly expensive.
A thousand parallel workers means a thousand simultaneous API calls to your LLM provider.
You are trading time for money.
And most importantly, for us, this is an orchestration nightmare.
This is not a simple for loop.
This is a complex asynchronous parallel system.
You must design for it.
What happens if worker 532 fails?
Does the whole job fail?
Do you retry just that one job?
What about API rate limits when you make a thousand calls at once?
This is a significant engineering challenge.
As a summary, we can say that the swarm pattern is one to n parallel processing model.
It is the MapReduce architecture for agents.
The components are a queen, which is the decomposer aggregator and worker executor agents.
Use case perfect for massive list based independent tasks.
Example of analyze a thousand of documents or process a thousands of images.
Trade offs are you trade cost and complexity for the speed and scale.
